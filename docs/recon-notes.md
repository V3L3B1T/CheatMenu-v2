## Dispatch site for `Hex.Session.TypeCmdResourceCheat` — Task 7 finding

### Direct enum search

`Hex.Session.TypeCmdResourceCheat` exists (values: `Add`, `Substract`, `AddAll`) but
**no public method on any type in `Hex.dll` takes the enum as a parameter**. The enum
appears to be a type tag for serialization or networking, not a function dispatch
key. The plan's spec (§6.2) anticipated this case — it routes to "Branch B" (Harmony
reverse-patch). However, recon found a **better path: drive the existing UI panel.**

### Selected dispatcher: `Hex.Cheat.UI.BhResourcePanel.AddAllResource()`

The dev cheat panel exposes a public, parameterless `AddAllResource()` method
that's the click handler for its "buy all resources" button. Its underlying logic
adds all 7 resources at once. There are matching private `AddGold()`, `AddWood()`,
`AddStone()`, `AddFerrum()`, `AddGlass()`, `AddIchor()`, `AddDust()` methods —
the seven Olden Era resources are: gold, wood, stone, ferrum, glass, ichor, dust.

**Strategy for Task 8 — "Branch C: drive the existing UI":**

1. Find an existing `BhResourcePanel` instance via `Resources.FindObjectsOfTypeAll<BhResourcePanel>()`
   (the cheat panel is part of the `BhWindowCheatPanel` hierarchy; even when hidden
   it's expected to be present in the loaded scene because the dev tools were
   shipped intact).
2. The amount comes from the panel's seven `inputFields` (TMP_InputField list, public
   getter `get_inputFields()`). Set each one's `text = "10000"` before invoking.
3. Call `panel.AddAllResource()` — this triggers the same path the dev's "buy all"
   button would. Network-replicates correctly because the panel's existing logic
   handles that.

**Fallback strategy ("Branch D: direct value mutation"):** if no `BhResourcePanel`
instance exists in any loaded scene (i.e., the cheat-panel prefab was stripped from
shipped Addressables), drop to direct mutation:
- `Hex.Session.Data.Resource` is an `Il2CppSystem.Object` with public `get_value()` /
  `set_value(int)`. Find the active player's resource list (likely hanging off
  `Hex.Session.*`), iterate, set each value += 10000.
- This path bypasses any network sync — only acceptable in single-player.

### What we did NOT do

- Did NOT decompile native code reached via `il2cpp_runtime_invoke` calls in
  `BhResourcePanel.AddAllResource()`'s IL2CPP wrapper. The IL preview shows only
  the standard interop trampoline; the real logic is in `GameAssembly.dll`. We
  treat `AddAllResource()` as a black box.
- Did NOT identify the underlying network-replication path. Branch C inherits
  whatever the dev panel does; Branch D bypasses it.

## Native cheat panel asset paths

**Tier 1 hit — Addressables and Resources.Load tiers not needed.**

`Resources.FindObjectsOfTypeAll<Hex.Cheat.BhControllerCheat>()` returns 3
instances on a loaded skirmish/campaign save (one each for world, city, battle
contexts — the first one is named `CheatWorld`). They're left in the shipped
scene hierarchy, just disabled. Calling `gameObject.SetActive(true)` then
`hrf()` (the native `BhScreen.Show` entry point) renders them.

Tier 2 (Addressables) and tier 3 (`Resources.Load`) from the original plan
are **not implemented** because:

1. `Unity.Addressables.dll` is absent from `BepInEx/interop/` on this build —
   the IL2CPP interop generator didn't emit it (probably because no game
   code we care about uses Addressables APIs in a public surface).
2. Tier 1 is sufficient — Hex's dev cheat tooling stays in the scene
   hierarchy in the shipped product.

If a future game patch strips the prefabs from shipped scenes, tiers 2/3
would need to be implemented. The `NativePanelDriver.TryFind()` method
would extend to: try `LoadAssetAsync<GameObject>("BhControllerCheat")` on
keys `["BhControllerCheat", "CheatPanel", "Cheat/BhControllerCheat",
"UI/CheatPanel"]`, then `Resources.Load<GameObject>` on the same set.

## IL2CPP interop quirks observed (cumulative)

- `UnityEngine.UI.dll`, `Unity.TextMeshPro.dll`, AND
  `UnityEngine.{Core,IMGUI,InputLegacy}Module.dll` must all be sourced from
  `BepInEx/interop/` rather than `BepInEx/unity-libs/`. The unity-libs/ versions
  are Mono stubs lacking the `IntPtr` constructor required for IL2CPP
  `MonoBehaviour` subclassing.
- `<Nullable>enable</Nullable>` in csproj fails to build against the IL2CPP
  CoreModule because it shadows `System.Runtime.CompilerServices.NullableAttribute`.
  Standard fix: `<Nullable>disable</Nullable>` and drop `null!` markers.
- Properties on injected `MonoBehaviour` classes get a getter proxy generated by
  Il2CppInterop; if the return type isn't marshallable (e.g., `IReadOnlyList<T>`,
  arrays of struct types like `Rect`), a `[Warning:Il2CppInterop]` is logged.
  Use plain public fields when the value only needs to be visible to other C#
  code, not the IL2CPP runtime.
